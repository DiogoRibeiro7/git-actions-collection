# Security Scan Compliance Guide

This guide explains how the `security-scan` reusable workflow supports common compliance frameworks such as SOC 2 and GDPR.

## Security Controls

- All third-party actions are pinned by commit SHA to mitigate supply-chain attacks.
- Workflow permissions are limited to `contents: read` and `security-events: write` to uphold least-privilege principles.
- SLSA Level 2 attestations are generated for scan artifacts and uploaded via the GitHub Attestation API.
- Each shell step enables `set -euo pipefail` and quotes variables to avoid command injection.
- Python-based scanners follow the shared pip upgrade policy: `24.3.1` is the validated default and the workflow exposes a `pip-version` input (set it to `latest` to track upstream) when you need a newer installer.

## Audit Logging

- Logs from `pip-audit` and `Bandit` are captured and uploaded as artifacts for traceability.
- A separate `audit.log` records run metadata (workflow name, run ID, commit, timestamp) to assist with regulatory audits.
- Attestation bundles produced by the workflow can be retained for external verification.

## Privacy and GDPR

- The workflow processes repository source code only; no personal data is collected or transmitted.
- Uploaded artifacts remain within the GitHub Actions environment and follow the repository's retention policy.

## Industry Requirements

- SARIF reports generated by the scan can be used as evidence for frameworks like SOC 2 or ISO 27001.
- Logs and artifacts provide an auditable trail demonstrating regular security scanning practices.
- Dependency signatures are verified for supported package managers (npm, Maven, Gradle, Go modules) to guard against tampering.
